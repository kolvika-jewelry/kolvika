# Уведомления о лидах KOLVIKA

Файл `lead-email-router.gs` предназначен для Google Apps Script, который обслуживает вкладку «Лиды с AI-лендингов» таблицы «Лиды и Оффлайн конверсии Колвика». Он не меняет действующий `doPost` или формы сайта.

Порядок включения после проверки проекта приёмника:

1. Убедиться, что в проекте пока нет отправки писем по этим лидам, чтобы не создать дубли.
2. Добавить код отдельным файлом в этот же проект Apps Script (или в отдельный проект с доступом к таблице).
3. Один раз выполнить `setupKolvikaLeadEmails` из учётной записи, от которой должны уходить письма, и разрешить доступ к таблице и MailApp.
4. Проверить, что в колонке P появился заголовок `Email-уведомление`, исторические строки помечены `ПРОПУЩЕНО`, а установлен один триггер `sendKolvikaLeadEmails` каждые 5 минут.
5. Отправить две синтетические тестовые заявки через обычные формы: ремонт и изготовление/переделка. Проверить строки P и получение писем обеими почтами. Тестовые строки и их удаление согласовать отдельно.

Важно: запись строк веб-приложением Apps Script не запускает триггер `onFormSubmit`; поэтому используется таймер. Маршрут определяется **только по полю «Лендинг»**: «Ремонт украшений» — на `info@kolvika.ru`, «Украшения на заказ» и «Квиз украшения на заказ» — на `jewelry@kolvika.ru`. Неизвестные обращения не отправляются наугад и получают отметку `ТРЕБУЕТ МАРШРУТА`. В теме письма соответственно «Заявка на ремонт» или «Заявка на изготовление».

Письма уходят от Google-аккаунта, в котором создан таймерный триггер. `MailApp` не позволяет произвольно подставить доменный адрес отправителя; для отправки *от* домена потребуется настроенный доменный Google Workspace-аккаунт или подтверждённый Gmail-псевдоним и отдельная схема через `GmailApp`. Это не нужно для текущего маршрута и не должно настраиваться без доступа к почтовому аккаунту.

## Яндекс ClientID

`lead-receiver.gs` — актуальная копия файла `Код.gs` действующего приёмника. Он записывает `ym_client_id` в Q (`Яндекс ClientID`) как текст, чтобы длинный идентификатор не округлялся в таблице. P остаётся для статуса email-уведомления. Формы всех трёх лендингов получают ClientID через `ym(112938684, 'getClientID', ...)` в общем `lead-analytics.js`. Если Метрика заблокирована, заявка отправляется с пустым ID.

После изменения `Код.gs` надо обновить **существующее** развёртывание веб-приложения, выбрав новую версию. Новое развёртывание создало бы другой URL и не подключилось бы к текущим формам.

## Подтверждение заявки для цели `lead_submit`

Форма передаёт случайный `request_id`, затем проверяет, появилась ли строка с этим ID. Только после ответа `saved: true` форма показывает успех и отправляет `lead_submit` в Метрику. Неподтверждённая заявка остаётся в форме для повтора с тем же ID; повторная запись не создаётся.

Порядок включения при повторном развёртывании:

1. На вкладке «Лиды с AI-лендингов» добавить столбец R с точным заголовком `ID заявки`. Столбцы P (`Email-уведомление`) и Q (`Яндекс ClientID`) не менять.
2. Сверить действующий `Код.gs` с `lead-receiver.gs`, перенести изменения подтверждения без потери более новых правок и обновить **существующее** развёртывание веб-приложения. Проверить через безопасный GET, что новое развёртывание работает; не отправлять реальные или тестовые заявки без отдельного согласования.
3. Только после этого публиковать обновлённые файлы трёх лендингов. Иначе новый фронтенд не получит подтверждение и будет показывать ошибку даже при успешной записи.

Подтверждение использует GET-ответ без персональных данных. Сам по себе успешный `fetch` с `no-cors` не считается подтверждением, поскольку ответ на такой запрос недоступен странице.

Если письмо ушло, но запись результата в P не сохранилась, при повторном запуске возможен дубль. Полная гарантия «ровно один раз» при работе двух независимых сервисов (MailApp и Sheets) недостижима без отдельной очереди; колонка P и блокировка уменьшают риск.
