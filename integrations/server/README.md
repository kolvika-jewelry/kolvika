# Приём заявок KOLVIKA на сервере

Формы трёх лендингов отправляют JSON на `/api/leads` своего домена. Nginx
передаёт запрос локальному сервису на `127.0.0.1:3210`. Сервис сохраняет
заявку в SQLite под `/var/lib/kolvika-leads/`, подтверждает сохранение форме и
отправляет её в amoCRM из фоновой очереди. При временной ошибке amoCRM заявка
остаётся на сервере и повторяется с задержкой.

## UTM-переходы

`utm-propagation.js` сохраняет последний входящий набор `utm_*` в cookie на
`.kolvika.jewelry` сроком на 30 дней. Новый URL с UTM заменяет предыдущий набор.
Ссылки между `custom`, `repair` и `quiz` получают эти параметры, если в целевом
URL уже нет собственных UTM. Внешние ссылки, телефоны и почта не изменяются.
Форма передаёт текущий сохранённый набор вместе с заявкой.

В карточку amoCRM всегда создаётся новая сделка. Перед созданием сервис ищет
контакт по точному нормализованному номеру телефона: если контакт найден,
новая сделка связывается с ним; если нет — контакт создаётся вместе со сделкой.
Текстовое примечание содержит лендинг, тип обращения, сообщение, страницу,
referrer и все UTM-поля. Каждая сделка получает тег `Jewerly` и тег лендинга по
хосту страницы: `custom`, `repair` или `quiz`. Получение ClientID Яндекс.Метрики
не задерживает отправку формы; ClientID добавляется, если уже доступен.
Чтобы записывать отдельные UTM в пользовательские поля сделки, задайте их ID в
`AMOCRM_LEAD_FIELD_IDS_JSON`, например `{"utm_source":123,"utm_campaign":456}`.
Воронку, этап и ответственного можно задать через переменные окружения.

В аккаунте `kolvika.amocrm.ru` полученный от Метрики `ym_client_id` по умолчанию
записывается в поле сделки `_ym_uid` (ID `2839145`), даже если в mapping заданы
только UTM. Непустое значение также остаётся в примечании. Отсутствие ClientID
не мешает отправить заявку: пустое значение в CRM не записывается. Для другого
аккаунта этот ID не применяется. Явный ключ `ym_client_id` в
`AMOCRM_LEAD_FIELD_IDS_JSON` имеет приоритет над значением по умолчанию.

Если код сервера ещё не обновлён, тот же результат можно получить настройкой:
добавьте `"ym_client_id":2839145` в **существующий** JSON в
`/etc/kolvika-leads.env`, сохранив остальные ключи, и перезапустите сервис.
Не заменяйте весь mapping одним ключом. Не публикуйте содержимое env-файла:
в нём находятся секреты.

### Применение исправления ClientID

Публикация GitHub Pages не обновляет приёмник на VPS. Сначала проверьте
действующий mapping: явный неправильный ключ `ym_client_id` нужно исправить,
поскольку он перекрывает значение по умолчанию. Если используется исправление
кода, установите проверенный `lead_service.py` поверх файла в
`/opt/kolvika-leads/`, предварительно сохранив предыдущую версию, и выполните:

```sh
systemctl restart kolvika-leads
systemctl is-active kolvika-leads
curl --fail http://127.0.0.1:3210/healthz
```

Не переустанавливайте сервис и не меняйте SQLite, очередь или OAuth-настройки.
Эта правка действует на новые сделки; старые автоматически не изменяет.
После применения отправьте одну согласованную техническую заявку и проверьте
значение **в поле** `_ym_uid`, а не только в примечании. Сравните его с тем же
ClientID в примечании, не публикуя значение. Если поле снова пустое, проверьте
актуальную конфигурацию запущенного процесса и CRM-автоматики, изменяющие поля.

Локальная проверка серверной передачи без запросов в CRM:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_lead_service.py' -v
```

## Установка

Создайте системного пользователя и каталог кода:

```sh
useradd --system --home /nonexistent --shell /usr/sbin/nologin kolvika-leads
install -d -o root -g root -m 0755 /opt/kolvika-leads
install -o root -g root -m 0644 lead_service.py /opt/kolvika-leads/lead_service.py
```

Заполните `/etc/kolvika-leads.env` на сервере по образцу `.env.example`. Файл
окружения должен быть доступен только root (`chmod 600`). В репозиторий можно
добавлять только пример без значений секретов.

Установите unit-файл `kolvika-leads.service` в
`/etc/systemd/system/kolvika-leads.service`, затем выполните:

```sh
systemctl daemon-reload
systemctl enable --now kolvika-leads
systemctl status kolvika-leads --no-pager
```

Добавьте содержимое `nginx-location.conf` внутрь HTTPS-vhost каждого из трёх
доменов, затем проверьте конфигурацию и примените её:

```sh
nginx -t
systemctl reload nginx
```

После сохранения `AMOCRM_CLIENT_ID` и `AMOCRM_CLIENT_SECRET` в
`/etc/kolvika-leads.env` создайте одноразовую ссылку OAuth от имени системного
пользователя сервиса:

```sh
systemd-run --wait --pipe --collect --unit=kolvika-oauth-link \
  --property=User=kolvika-leads \
  --property=Group=kolvika-leads \
  --property=WorkingDirectory=/opt/kolvika-leads \
  --property=EnvironmentFile=/etc/kolvika-leads.env \
  /usr/bin/python3 /opt/kolvika-leads/lead_service.py oauth-link
```

Откройте полученную ссылку под администратором аккаунта и разрешите доступ.
Callback сам обменяет временный код на токены и сохранит их в SQLite.

Сервис слушает только loopback и не открывает новый публичный порт.
Проверить состояние из shell сервера можно запросом
`curl http://127.0.0.1:3210/healthz`; в ответе нет данных заявок или секретов.

## Настройка amoCRM

Если у существующей интеграции уже создан долгосрочный токен, задайте
`AMOCRM_LONG_LIVED_TOKEN` и `AMOCRM_ACCOUNT_URL`; Redirect URI и client secret
для этого режима не нужны. Сервис передаёт токен как Bearer access token.
Срок токена выбирается при создании — от 1 дня до 5 лет; токен можно отозвать.
Храните его в `/etc/kolvika-leads.env` с правами `600`. При истечении срока или
отзыве замените токен и перезапустите сервис.

Для новой приватной интеграции в аккаунте `kolvika.amocrm.ru` используйте
следующие настройки:

- название: `KOLVIKA — заявки с лендингов`;
- разрешение: `Данные аккаунта`;
- Redirect URI: `https://custom.kolvika.jewelry/api/amocrm/callback`;
- контроль дублей: выключен, так как сервис сам ищет существующий контакт и
  всегда создаёт новую сделку;
- описание: `Приём заявок с трёх лендингов KOLVIKA и передача в CRM с UTM`.

Загрузку логотипа, URL отключения интеграции, доступ к файлам и центру
уведомлений оставьте пустыми/выключенными. После создания передайте
`AMOCRM_CLIENT_ID` и `AMOCRM_CLIENT_SECRET` через защищённый запрос BB, а не в
чат. Временная ссылка авторизации будет сформирована на сервере; после того как
администратор аккаунта разрешит доступ, callback обменяет код на токены и
сохранит их в локальной SQLite базе. Коды и токены не пишутся в журналы.

Если используется уже существующая интеграция с другим Redirect URI, не меняйте
его, пока не проверено, что он не нужен другим сервисам. Укажите в конфигурации
его точное текущее значение и используйте Authorization code из интерфейса
amoCRM через одноразовую команду `lead_service.py oauth-code`; эта команда
обменивает код и сохраняет токены на сервере без перенаправления на наш callback.
Одноразовый код передавайте только во временном root-only EnvironmentFile и
удаляйте этот файл сразу после обмена.

Переменные `AMOCRM_PIPELINE_ID`, `AMOCRM_STATUS_ID` и
`AMOCRM_RESPONSIBLE_USER_ID` необязательны. После OAuth-настройки сервис
сверяет числовые ID воронки «Квалификация» и этапа «Новая заявка»; ответственный
остаётся по настройкам аккаунта, если отдельный ID не задан.

Приёмник дедуплицирует технические повторы одного `request_id` до постановки в
очередь. Повторные заявки с одного телефона создают новые сделки с найденным
контактом.

Сервис принимает заявки только с HTTPS-origin трёх доменов KOLVIKA и ограничивает
частоту отправок с одного IP. Все данные заявок и очередь хранятся локально в
SQLite. Исторические строки из прежней Google-таблицы автоматически не
импортируются.

Страницы, открытые на `kolvika-jewelry.github.io`, не имеют доступа к этому
серверному API. Отправка форм работает на трёх доменах KOLVIKA после установки
сервиса и Nginx location.
